## 1-③ 햄버거 메뉴, 스크롤 애니메이션, 맨 위로 가기 버튼

**보여줄 방법** — 모바일 폭에서 햄버거 클릭 → 메뉴 항목 클릭 → 스크롤 내리기 → 우하단 ↑ 버튼

**확인 포인트** — 햄버거가 X로 변형, 섹션이 스르륵 나타남, 300px 넘으면 ↑ 버튼 등장

**읽을 말 — 세 개를 각각 다른 방식으로 만들었습니다**

> "세 기능이 **일부러 다른 방식**입니다.
>
> **① 햄버거**는 상태 하나(`state.isMenuOpen`)로 돌아갑니다.
> 아이콘 모양, 메뉴 열림, `aria-expanded` 속성이 **전부 그 하나를 보고** 바뀝니다.
>
> **② 스크롤 등장 애니메이션**은 `scroll` 이벤트를 쓰지 않았습니다.
> **`IntersectionObserver`**를 썼습니다. '이 요소가 화면에 20% 이상 들어왔는가'를
> **브라우저가 알려주게** 하는 겁니다. 스크롤 이벤트로 위치를 직접 계산하면
> 1초에 수십 번 계산해야 하는데, 이건 브라우저가 필요할 때만 불러줍니다.
>
> **③ 맨 위로 버튼과 스크롤 스파이**는 `scroll` 이벤트가 필요했습니다.
> 그런데 **`scroll`은 1초에 수십 번 발생합니다.** 그래서
> `requestAnimationFrame`으로 **'다음 화면 그리기 직전에 한 번만'** 계산하도록 묶었습니다."
>
> ```js
> let ticking = false;
> window.addEventListener('scroll', () => {
>   if (ticking) return;        // 이미 예약돼 있으면 무시
>   ticking = true;
>   window.requestAnimationFrame(() => { handleScroll(); ticking = false; });
> });
> ```
>
> "안 묶으면 **스크롤할 때 화면이 버벅입니다.** 브라우저가 그림을 그릴 틈에
> 계산이 계속 끼어들어서요."

### ★ 이걸 말하면 가산점: `fetch`의 함정

> "**`fetch`는 404나 403이 와도 `catch`로 가지 않습니다.**
> 네트워크 자체가 실패했을 때만 reject하고, 404는 '서버가 정상적으로 답을 준 것'으로 봅니다.
>
> 그래서 `response.ok`를 **직접 확인**하고 제가 `throw`를 던져서
> 아래 `catch`에서 함께 처리되게 했습니다. 403은 호출 한도 초과,
> 404는 사용자 없음으로 **메시지를 나눠뒀습니다.**
>
> 그리고 인터넷이 끊기면 `TypeError`로 **`Failed to fetch`**라는 기술적인 메시지가 오는데,
> 사용자에게는 **'네트워크 연결을 확인해 주세요'**로 바꿔서 보여줍니다."

### ★ 또 하나의 가산점: XSS

> "저장소 설명을 `innerHTML`에 그냥 넣으면 **태그 문자열이 실행될 수 있습니다(XSS).**
> 그래서 `escapeHtml()`로 `< > & " '`를 엔티티로 바꿔서 넣습니다.
> **외부에서 온 데이터는 전부** 이 함수를 통과합니다."

# 🟦 항목 2 — 구조와 선택의 이유

## 2-1. HTML/CSS/JS를 각각의 파일로 분리한 이유

> "역할이 다르기 때문입니다. HTML은 **구조와 의미**, CSS는 **표현**, JS는 **동작**입니다.
> 분리하면 세 가지 이점이 있습니다.
> ① 디자인을 바꿀 때 **HTML을 건드리지 않아도** 됩니다.
> ② CSS와 JS 파일은 브라우저가 **캐시**해서 재방문 시 다시 받지 않습니다.
> ③ 문제가 생겼을 때 **어느 파일을 봐야 하는지** 바로 압니다.
>
> 저는 JS를 한 단계 더 나눠서, **바뀌는 값(`config.js`)과 로직(`main.js`)**을 분리했습니다.
> 이름이나 기준값을 고칠 때 **로직 파일을 열지 않아도** 되니까요."

## 2-2. 시맨틱 태그를 어떤 기준으로 선택했는가

> "**'이 덩어리에 제목을 붙일 수 있나?'**를 기준으로 잘랐습니다.
> 제목을 붙일 수 있는 주제 단위는 `section`으로 하고 `id`를 줘서
> **네비게이션 앵커의 목적지**로 썼습니다.
>
> `header`는 사이트 머리말, `nav`는 탐색 링크 묶음, `main`은 본문 한 덩어리,
> `footer`는 저작권·소셜 링크입니다.
>
> 프로젝트 카드는 **떼어놔도 그 자체로 말이 되는** 독립 콘텐츠라서
> `section`이 아니라 **`article`**을 썼습니다.
>
> `div`를 쓰지 않은 이유는, `div`는 **아무 의미가 없어서**
> 스크린리더도 검색엔진도 그게 뭔지 알 수 없기 때문입니다."

> ⚠️ 평가자가 **"article이 index.html에 없는데요?"**라고 하면
> → "카드는 GitHub API 응답으로 만들어지는 **동적 요소**라 JS 템플릿 안에 있습니다.
> Elements 탭 보시면 있습니다." (`createProjectCard()`)

## 2-3. CSS 변수(`:root`)로 관리하면 어떤 이점이 있는가

> "세 가지입니다.
> ① **한 곳만 고치면 전체가 바뀝니다.** 메인 색을 바꾸려면 `--color-primary` 한 줄만
> 고치면 버튼·링크·강조 텍스트가 모두 따라옵니다.
> ② **다크 모드를 규칙 재작성 없이** 만들 수 있습니다.
> ③ `--space-4` 같은 이름을 쓰면 **간격이 제멋대로 벌어지는 걸 막아** 일관성이 유지됩니다.
>
> 예전처럼 `#4f46e5`를 30군데 복붙했다면, **색 하나 바꾸는 데 30군데를 찾아야 하고
> 하나쯤 빠뜨립니다.**"

## 2-4. `onclick` 대신 `addEventListener`를 쓴 이유

> "네 가지 차이가 있습니다.
> **① 관심사 분리** — `onclick`은 HTML 안에 자바스크립트가 섞입니다.
> **② 중복 등록** — `onclick`은 **하나만** 붙습니다. 두 번 지정하면 나중 것이 앞의 것을 덮어씁니다.
> `addEventListener`는 같은 이벤트에 **여러 함수**를 붙일 수 있습니다.
> **③ 해제와 옵션** — `removeEventListener`로 뗄 수 있고, `once`·`passive` 옵션도 줍니다.
> **④ 이벤트 종류의 폭** — `scroll`, `submit`, `input`처럼 `on~` 속성으로 다루기 번거로운 것도 동일하게 다룹니다.
>
> 실제로 제 코드에서 **'다시 시도' 버튼은 JS가 나중에 만드는 요소**라
> HTML에 `onclick`을 쓸 수조차 없습니다. **이벤트 위임**으로 처리했습니다."

## 3-2. `async/await` + `try/catch`로 성공/실패를 어떻게 분기했는가

```js
const fetchProjects = async () => {
  setProjectsState({ status: 'loading', error: '' });        // ① 요청 전: 로딩 상태
  try {
    const response = await fetch(GITHUB_API_URL);            // ② 응답 올 때까지 대기
    if (!response.ok) {                                      // ③ 404·403은 catch로 안 감!
      if (response.status === 403) throw new Error('호출 한도 초과…');
      if (response.status === 404) throw new Error('사용자를 찾을 수 없음…');
      throw new Error(`요청 실패 (HTTP ${response.status})`);
    }
    const repos = await response.json();                     // ④ 본문 파싱 대기
    const myRepos = [...repos].filter(r => !r.fork)          // ⑤ 가공
                              .sort((a,b) => b.stargazers_count - a.stargazers_count);
    setProjectsState({ status: 'success', items: myRepos }); // ⑥ 성공 상태
  } catch (err) {                                            // ⑦ 실패 상태
    const message = err instanceof TypeError ? '네트워크 연결을 확인해 주세요.' : err.message;
    setProjectsState({ status: 'error', items: [], error: message });
  }
};
```

> "`await`는 응답이 올 때까지 **이 함수만** 잠시 멈춥니다. **페이지는 계속 동작합니다.**
>
> 중요한 함정이 하나 있는데, **`fetch`는 404나 403이 와도 catch로 가지 않습니다.**
> 그래서 `response.ok`를 직접 확인하고 제가 `throw`를 던집니다.
>
> 그리고 성공이든 실패든 결과는 전부 **상태값 하나(`status`)로 수렴**시켜서,
> 화면 그리는 곳은 `renderProjects()` **한 군데**뿐입니다."

## 3-3. `map`/`filter`로 GitHub 데이터를 카드 UI로 바꾸는 과정

| 단계 | 코드 | 설명 |
|---|---|---|
| ① 받기 | `await response.json()` | 저장소 **객체 배열**을 받습니다 |
| ② 거르기 | `.filter(repo => !repo.fork)` | 포크한 건 제 작업이 아니라 제외. `filter`는 **조건에 맞는 것만 담은 새 배열** |
| ③ 고르기 | `activeLanguage === 'All' ? items : items.filter(...)` | 필터 버튼 상태에 따라. **원본은 그대로** 두니 All을 누르면 즉시 복구 |
| ④ 바꾸기 | `visible.map(createProjectCard)` | `map`은 **각 요소를 다른 값으로 바꿔 새 배열**. 저장소 객체 → 카드 HTML 문자열 |
| ⑤ 붙이기 | `.join('')` → `grid.innerHTML = ...` | 조각을 하나로 합쳐 **한 번만** DOM에 넣습니다 |

**꼬리 질문 대비**

- **"왜 `join('')`을 쓰나요?"** → "`map`의 결과는 배열이라 그냥 넣으면 **요소 사이에 쉼표**가 들어갑니다."
- **"반복문 안에서 `innerHTML +=` 하면 안 되나요?"** → "동작은 하지만 **매번 기존 HTML을 다시 파싱해서 DOM을 새로 만듭니다.** 카드가 많아질수록 느려집니다. 한 번에 넣으면 DOM 갱신이 1회로 끝납니다."
- **"`({ name, html_url, ... })`는 뭔가요?"** → "**구조분해 할당**입니다. `repo.name`을 매번 쓰지 않아도 되고, 이 함수가 **객체의 어떤 필드를 쓰는지 매개변수만 봐도** 드러납니다."
- **"외부 데이터를 `innerHTML`에 그냥 넣어도 되나요?"** → "안 됩니다. 설명에 태그 문자열이 있으면 실행될 수 있어서(**XSS**) `escapeHtml()`로 바꿔서 넣습니다." ← **가산점**

## 3-4. Flexbox와 Grid를 각각 어디에, 왜 선택했는가

> "판단 기준은 **차원**입니다. **한 줄(1차원)로 늘어놓는 배치는 Flexbox**,
> **행과 열을 동시에 잡는 격자(2차원)는 Grid**를 썼습니다."

| 위치 | 선택 | 이유 |
|---|---|---|
| 네비게이션 | **Flexbox** | 로고와 메뉴를 **한 줄**에 놓고 양 끝으로 밀면 됨. `justify-content: space-between` 한 줄. 항목 개수가 바뀌어도 알아서 배치 |
| 프로젝트·스킬 카드 | **Grid** | 카드가 **행과 열로 채워지는 격자**. `repeat(auto-fit, minmax(280px, 1fr))`로 **미디어 쿼리 없이** 1→2→3열 |
| About 섹션 | **Grid** | 사진과 글의 **2열 틀을 먼저 정하고** 채우는 구조. `grid-template-columns: 260px 1fr` |
| 카드 내부 | **Flexbox** (`column`) | 제목·설명·메타를 **세로 한 줄**로 쌓고, 설명에 `flex: 1`을 줘서 카드 높이를 맞춤 |

> 💡 **"Flex로도 격자를 만들 수 있지 않나요?"**가 자주 나옵니다.
> → "만들 수 있지만 `flex-wrap`으로 줄바꿈시키면 **마지막 줄 정렬이 어긋납니다.**
> Grid는 **열 개수를 컨테이너가 관리**해서 그런 문제가 없습니다."

## 4-2. 반응형에서 "모바일 퍼스트"로 작성한 이유

# 🟦 마지막 — "경험 정도 (재구현 가능 여부)"

평가표 맨 아래에서 평가자가 **다시 만들 수 있는 수준인지** 체크합니다.
여기서 좋은 평가를 받으려면 **"만들 때 겪은 시행착오"**를 한두 개 말하는 게 가장 효과적입니다.

**쓸 수 있는 실제 시행착오 3가지**

**① 에러가 났는데 이전 카드가 남아 있던 문제**
> 로딩을 지우는 곳과 카드를 그리는 곳이 달라서 생겼습니다.
> `renderProjects()` 하나가 상태에 따라 **항상 전체를 다시 그리도록** 바꿔서 해결했습니다.

**② 햄버거 아이콘이 X가 아니라 꺾쇠(>)로 보이던 문제**
> 버튼이 `display: grid`였는데, 그리드가 남는 높이를 행에 나눠 가지면서
> 막대 간격이 설정한 5px보다 벌어졌습니다. 그래서 회전시켰을 때
> 두 막대가 가운데에서 만나지 못했습니다.
> `flex-direction: column`으로 바꿔 간격을 고정해 해결했습니다.

**③ 새로고침할 때 다크 모드가 한 번 깜빡이는 것**
> `defer` 스크립트는 HTML 파싱 후 실행되니 그 직전 한 프레임이 라이트로 보일 수 있습니다.
> `<head>`에 인라인 스크립트를 넣으면 없앨 수 있지만, 과제 요구사항인
> "JS는 defer로 연결"을 지키려고 **알고도 감수한 트레이드오프**입니다.

> 💡 **③번처럼 "알고 있지만 이런 이유로 선택하지 않았다"**를 말할 수 있으면
> 재구현 가능한 사람으로 보입니다.
