# 02. 예상 질문 & 답변

> 과제 문서의 "**과제 목표: 학습자가 스스로 설명할 수 있어야 한다**" 6개 항목을 모두 포함했습니다.
> ⭐ 는 거의 반드시 나오는 질문입니다. 소리 내어 답하는 연습을 하세요.

## A. HTML / 시맨틱

**⭐ Q1. `div` 대신 시맨틱 태그를 쓰는 이유가 뭔가요?**
`div`는 아무 의미가 없는 상자입니다. `header`, `nav`, `main`, `section`, `article`, `footer`는
태그 이름 자체가 그 영역의 역할을 설명합니다. 이점이 세 가지입니다.
1) **접근성** — 스크린리더가 "탐색 영역", "본문"으로 인식해 사용자가 건너뛸 수 있습니다.
2) **검색엔진** — 어디가 본문인지 기계가 판단할 수 있습니다.
3) **협업/유지보수** — 닫는 태그만 봐도 어떤 블록이 끝났는지 알 수 있습니다.

**Q2. 구조는 어떤 기준으로 나눴나요?**
"화면에서 제목을 붙일 수 있는 독립된 덩어리"를 `section` 하나로 잡았습니다.
그래서 Hero / About / Skills / Projects / Contact 다섯 개 섹션이 되고, 각각 `id`를 줘서
네비게이션 앵커(`href="#about"`)의 목적지로 씁니다.
프로젝트 카드 하나하나는 그 자체로 독립적으로 의미가 통하는 콘텐츠라서 `article`을 썼습니다.

**Q3. `section`과 `article`의 차이는?**
`section`은 문서의 한 부분(주제 단위), `article`은 그것만 떼어내도 말이 되는 독립 콘텐츠입니다.
카드 하나를 다른 페이지에 옮겨 놓아도 "저장소 이름 + 설명 + 스타 수"로 의미가 통하므로 `article`입니다.

**Q4. 이미지 `alt`는 왜 그렇게 썼나요?**
"프로필 사진" 같은 설명은 도움이 안 됩니다. 이미지가 안 보이는 상황에서 그 자리를 대신할 수 있는
문장이어야 하므로 "노트북 앞에 앉아 코드를 작성하는 해은의 일러스트 프로필"처럼 적었습니다.
반대로 장식용 아이콘(SVG)에는 `aria-hidden="true"`를 줘서 낭독기가 읽지 않게 했습니다.

**Q5. `label`의 `for`는 왜 필요한가요?**
`for="email"`이 `id="email"`인 입력창과 연결됩니다. 라벨을 클릭해도 입력창이 포커스되고,
스크린리더가 입력창에 도달했을 때 "이메일"이라고 읽어 줍니다. 연결이 없으면 무슨 칸인지 알 수 없습니다.

**Q6. 스크립트에 `defer`를 왜 붙였나요?**
`defer`가 없으면 브라우저가 HTML 파싱을 멈추고 스크립트를 먼저 실행합니다. 그러면 아직 만들어지지 않은
요소를 `querySelector`로 찾게 되어 `null`이 됩니다. `defer`는 다운로드는 병렬로 하되 실행은
HTML 파싱이 끝난 뒤로 미루고, **작성한 순서대로** 실행합니다. 그래서 `config.js` → `main.js` 순서가 보장됩니다.

## B. CSS / 레이아웃

**⭐ Q7. Flexbox와 Grid의 차이, 어디에 무엇을 썼나요?**
- **Flexbox = 1차원**(한 줄 또는 한 열). 내용 크기에 맞춰 배치할 때 좋습니다.
  → 네비게이션(로고 왼쪽, 메뉴·버튼 오른쪽), 버튼 그룹, 카드 내부 세로 배치에 썼습니다.
- **Grid = 2차원**(행과 열을 동시에). 격자 틀을 먼저 정하고 채울 때 좋습니다.
  → 프로젝트/스킬 카드 격자, About의 "사진 | 글" 2열 레이아웃에 썼습니다.
판단 기준은 "한 줄로 늘어놓는가(Flex) vs 격자 틀이 먼저 있는가(Grid)"입니다.

**⭐ Q8. `repeat(auto-fit, minmax(280px, 1fr))`가 무슨 뜻인가요?**
"카드 최소 너비는 280px, 남는 공간은 똑같이 나눠 갖고(1fr), 들어갈 수 있는 만큼 열을 자동으로 만들어라"
는 뜻입니다. 덕분에 카드 격자는 **미디어 쿼리 없이** 화면 폭에 따라 1열 → 2열 → 3열로 알아서 바뀝니다.

**⭐ Q9. 모바일 퍼스트가 뭐고 왜 그렇게 했나요?**
기본 CSS를 모바일 기준으로 쓰고, `@media (min-width: 768px)`로 넓은 화면 규칙을 **더하는** 방식입니다.
- 모바일은 보통 레이아웃이 단순(1열)해서 기본 스타일이 짧아집니다.
- 작은 기기가 불필요한 데스크톱 규칙을 해석하지 않아도 됩니다.
- 반대로(데스크톱 퍼스트) 하면 `max-width`로 계속 덮어쓰게 되어 규칙이 서로 충돌하기 쉽습니다.
브레이크포인트는 과제 기준대로 768px(태블릿), 1024px(데스크톱)입니다.

**⭐ Q10. CSS 변수는 왜 쓰나요? 다크 모드와 어떤 관계인가요?**
`:root`에 `--color-bg` 같은 이름으로 값을 한 번 정의해 두고 모든 규칙이 그 이름을 참조합니다.
다크 모드는 `[data-theme="dark"]` 안에서 **같은 이름에 다른 값만** 다시 정의합니다.
그래서 컴포넌트 CSS는 한 벌만 작성하면 두 테마 모두에서 동작합니다.
변수가 없었다면 다크 모드용 규칙을 전부 다시 써야 했을 겁니다.

**Q11. 인라인 스타일을 안 쓴 이유는?**
과제 제약이기도 하지만, 실무적으로도 인라인 스타일은 우선순위가 너무 높아 CSS로 덮기 어렵고,
구조(HTML)와 표현(CSS)이 섞여 유지보수가 어렵습니다.
그래서 스킬 게이지 너비도 JS가 `data-level="80"` 값만 넣고, 실제 `width: 80%`는
CSS의 속성 선택자 `.skill__bar[data-level="80"]`가 결정하도록 했습니다.

**Q12. `position: fixed` 헤더 때문에 제목이 가려지지 않나요?**
가려집니다. 그래서 각 섹션에 `scroll-margin-top: var(--header-height)`를 줘서
앵커로 이동했을 때 헤더 높이만큼 여유를 두고 멈추게 했습니다.

**Q13. `transition`은 어디에 걸었나요?**
버튼·카드의 hover(배경색, 그림자, `translateY`), 테마 전환 시 배경/글자색, 메뉴 열림/닫힘에 걸었습니다.
단, `prefers-reduced-motion: reduce`인 사용자는 애니메이션을 불편해할 수 있어
미디어 쿼리로 모든 전환을 사실상 끄도록 했습니다.

## C. JavaScript 기본 / DOM

**⭐ Q14. `querySelector`로 선택하고 `addEventListener`로 연결하는 흐름을 설명해 주세요.**
1) `document.querySelector('#theme-toggle')`로 CSS 선택자와 같은 문법으로 요소를 찾아 변수에 담습니다.
2) 그 요소에 `addEventListener('click', 콜백)`으로 "클릭이 일어나면 이 함수를 실행해 달라"고 등록합니다.
3) 사용자가 클릭하면 브라우저가 콜백을 호출하고, 콜백 안에서 상태를 바꾼 뒤 렌더 함수를 부릅니다.
4) 렌더 함수가 `setAttribute`나 `classList.toggle`로 DOM을 바꾸면 화면이 갱신됩니다.
제 코드에서는 자주 쓰는 요소를 `elements` 객체에 한 번만 찾아 담아 둡니다. `querySelector`는
호출할 때마다 문서를 탐색하기 때문에 반복 호출을 줄이려는 것입니다.

**Q15. `querySelector`와 `querySelectorAll`의 차이는?**
`querySelector`는 조건에 맞는 **첫 번째 요소 하나**, `querySelectorAll`은 **NodeList**(유사 배열)를 돌려줍니다.
NodeList에는 `forEach`는 있지만 `map`, `filter`는 없어서, 필요하면 `[...nodeList]`로 배열로 바꿔 씁니다.
(스크롤 스파이에서 `[...$$('main section[id]')]`로 변환한 부분이 그 예입니다.)

**⭐ Q16. `textContent`와 `innerHTML`은 어떻게 구분해서 썼나요?**
- `textContent`: 글자만 넣을 때. 태그로 해석되지 않아 안전하고 빠릅니다. (타이핑 효과, 에러 메시지, 연도)
- `innerHTML`: HTML 구조를 통째로 그려 넣을 때. (카드 목록, 상태 박스)
`innerHTML`은 문자열이 태그로 해석되므로, GitHub에서 받은 저장소 이름·설명은 반드시
`escapeHtml()`로 `<`, `>`, `&` 등을 바꿔서 넣습니다. 안 그러면 XSS 위험이 있습니다.

**Q17. `classList.add/remove/toggle`은 왜 쓰나요?**
JS는 "상태가 열렸다/보인다"만 클래스로 표시하고, 실제 모양은 CSS가 정합니다.
관심사를 분리하면 디자인을 바꿀 때 JS를 건드릴 필요가 없습니다.
`toggle(className, boolean)`처럼 두 번째 인자를 주면 "상태값에 맞춰 켜거나 끄기"를 한 줄로 쓸 수 있어
`state.isMenuOpen`을 그대로 넘기고 있습니다.

**Q18. `var`를 안 쓰고 `const`/`let`만 쓴 이유는?**
`var`는 함수 스코프라서 `if`나 `for` 블록을 벗어나서도 살아 있고, 재선언도 가능해 실수를 잡아주지 못합니다.
`const`/`let`은 블록 스코프이고 `const`는 재할당을 막아 줍니다.
기본을 `const`로 쓰고, 값이 바뀌어야 하는 것만 `let`으로 썼습니다. (`charIndex`, `ticking` 등)

**Q19. `const`로 선언한 `state` 객체의 값은 왜 바뀔 수 있나요?**
`const`는 "변수가 가리키는 대상을 바꿀 수 없다"는 뜻이지 "내용을 못 바꾼다"는 뜻이 아닙니다.
`state = {}` 는 에러지만 `state.theme = 'dark'` 는 가능합니다.

**Q20. `onclick` 속성 대신 `addEventListener`를 쓰는 이유는?**
1) HTML(구조)에 동작이 섞이지 않습니다.
2) `onclick`은 하나만 등록되고 나중 것이 앞의 것을 덮어쓰지만, `addEventListener`는 여러 개를 붙일 수 있습니다.
3) `removeEventListener`로 해제할 수 있고, 옵션(`once`, `passive` 등)도 줄 수 있습니다.

**⭐ Q21. `event.preventDefault()`는 어디에, 왜 썼나요?**
두 군데입니다.
1) 네비게이션 링크 클릭 — 기본 동작은 해당 앵커로 "즉시 점프"인데, 이걸 막고
   `scrollIntoView({behavior:'smooth'})`로 부드럽게 이동시키려고요.
2) 폼 제출 — 기본 동작은 페이지 새로고침(서버 전송)인데, 막지 않으면 화면이 초기화되어
   검증 결과도 성공 메시지도 볼 수 없습니다.

**Q22. 이벤트 위임(delegation)이 뭔가요?**
자식 각각에 리스너를 다는 대신, **부모에 한 번만** 걸고 `event.target`으로 누가 눌렸는지 판별하는 방식입니다.
'다시 시도' 버튼과 필터 버튼은 JS가 나중에 만들기 때문에 초기에는 존재하지 않아
리스너를 걸 수 없습니다. 그래서 항상 존재하는 부모(`#projects-status`, `#filters`)에 걸었습니다.
필터 쪽은 버튼 안의 글자를 클릭해도 잡히도록 `event.target.closest('.filter-btn')`를 씁니다.

**Q23. 스크롤 이벤트는 왜 그대로 쓰지 않았나요?**
스크롤 이벤트는 1초에 수십 번 발생합니다. 그때마다 위치 계산과 DOM 조작을 하면 버벅입니다.
그래서 `requestAnimationFrame`으로 "다음 화면 그리기 직전에 한 번만" 실행되도록 묶었습니다
(`ticking` 플래그). 이런 기법을 스로틀링이라고 합니다.

**Q24. Intersection Observer는 왜 썼나요? 스크롤 이벤트로도 되지 않나요?**
됩니다. 하지만 스크롤할 때마다 모든 요소의 위치를 직접 계산해야 하고, 그 계산이
레이아웃 재계산(reflow)을 유발해 성능에 나쁩니다. Intersection Observer는
"이 요소가 화면에 20% 이상 들어오면 알려줘"라고 브라우저에 맡기는 방식이라 훨씬 효율적입니다.
한 번 나타난 요소는 `unobserve`로 감시를 해제해 불필요한 호출을 줄였습니다.

## D. ES6+ 문법

**⭐ Q25. 화살표 함수는 왜 쓰나요?**
1) 짧습니다. `const $ = (sel) => document.querySelector(sel)`
2) 자신만의 `this`를 만들지 않고 바깥 `this`를 그대로 씁니다. 콜백 안에서 `this`가 달라지는
   전통적인 함정을 피할 수 있습니다.
다만 화살표 함수에는 `this`, `arguments`가 없으므로 생성자나 메서드로는 쓰지 않습니다.

**⭐ Q26. 구조분해 할당은 어디에 썼고 왜 필요한가요?**
카드를 만드는 함수에서 씁니다.
```js
const createProjectCard = ({ name, html_url, description, language, stargazers_count }) => `...`;
```
`repo.name`, `repo.html_url` … 을 매번 쓰지 않아도 되고, **이 함수가 객체의 어떤 필드를 쓰는지
매개변수만 봐도 드러난다**는 게 더 큰 장점입니다.
Intersection Observer 콜백의 `({ isIntersecting, target })`, `const { taglines } = PROFILE` 도 같은 이유입니다.

**⭐ Q27. `map`, `filter`, `forEach`의 차이와 사용처는?**
- `map`: 배열의 각 요소를 **다른 값으로 바꿔 새 배열**을 만듭니다. → 저장소 객체 배열 → HTML 문자열 배열
- `filter`: **조건에 맞는 것만 골라 새 배열**을 만듭니다. → 포크 제외(`!repo.fork`), 언어별 필터
- `forEach`: 반환값 없이 **각 요소에 대해 작업만** 합니다. → 링크마다 이벤트 등록, 필드마다 검증
`map`/`filter`는 원본 배열을 바꾸지 않아서, 필터를 풀면 원래 목록이 그대로 돌아옵니다.

**Q28. 템플릿 리터럴은 왜 쓰나요?**
백틱(`` ` ``) 문자열은 여러 줄을 그대로 쓸 수 있고 `${}`로 값을 끼워 넣을 수 있습니다.
따옴표 이어붙이기(`'<div>' + name + '</div>'`)보다 HTML 구조가 눈에 보여 실수가 적습니다.

**Q29. `map(...).join('')`을 쓴 이유는? 반복문 안에서 `innerHTML +=` 하면 안 되나요?**
동작은 하지만 느립니다. `innerHTML +=`는 **매번** 기존 HTML을 문자열로 만들고 다시 파싱해
DOM 전체를 새로 만듭니다. `map`으로 문자열 조각을 다 만든 뒤 `join('')`으로 합쳐
**한 번만** `innerHTML`에 넣으면 DOM 갱신이 한 번으로 끝납니다.

**Q30. `...`(스프레드)는 어디에 썼나요?**
1) `{ ...state.projects, ...partial }` — 기존 상태를 복사한 뒤 바뀐 값만 덮어씁니다.
2) `[...repos]` — 원본을 건드리지 않으려고 복사본을 만든 뒤 정렬합니다. (`sort`는 원본을 바꿉니다)
3) `['All', ...new Set(...)]` — Set으로 중복 제거한 뒤 배열로 펼칩니다.

**Q31. `??`(널 병합)와 `||`의 차이는?**
`||`는 `0`, `''`, `false`도 "거짓"으로 보고 오른쪽 값을 씁니다.
`??`는 `null`과 `undefined`일 때만 오른쪽 값을 씁니다.
저장된 테마를 읽을 때 `saved ?? (prefersDark ? 'dark' : 'light')`처럼 쓴 이유는
"값이 없을 때만" 시스템 설정을 따르게 하기 위해서입니다.

## E. 비동기 / API ★ 가장 많이 물어보는 영역

**⭐ Q32. `fetch`와 `async/await`의 흐름을 설명해 주세요.**
`fetch`는 요청을 보내고 **Promise**를 즉시 반환합니다. 응답을 기다리는 동안 브라우저는 멈추지 않습니다.
`await`는 그 Promise가 끝날 때까지 이 함수의 실행만 잠시 멈춥니다(페이지는 계속 동작).
```js
const response = await fetch(url);   // ① 응답 헤더 도착까지 대기
const repos = await response.json(); // ② 본문을 JSON으로 파싱할 때까지 대기
```
`await`를 쓰려면 함수에 `async`를 붙여야 합니다. `.then()` 체인보다 위에서 아래로 읽혀서 골랐습니다.

**⭐ Q33. 로딩/성공/에러/빈 상태를 어떻게 UI로 표현했나요?**
상태 값을 하나 두고(`state.projects.status`), 렌더 함수가 그 값에 따라 다른 화면을 그립니다.
```js
setProjectsState({ status: 'loading' });   // 요청 직전
...
setProjectsState({ status: 'success', items }); // 성공
...
setProjectsState({ status: 'error', error: message }); // 실패
```
- loading → 스피너 + 스켈레톤
- success + `items.length === 0` → 빈 상태 안내
- success + 데이터 있음 → 필터 + 카드 그리드
- error → 메시지 + 다시 시도 버튼
화면을 그리는 곳이 `renderProjects()` 한 곳이라, 상태가 꼬여 두 화면이 겹쳐 보이는 일이 없습니다.

**⭐ Q34. `fetch`는 404가 나도 `catch`로 안 간다던데요?**
맞습니다. `fetch`는 **네트워크 자체가 실패했을 때만** reject 합니다.
404, 403 같은 응답은 "서버가 정상적으로 답을 준 것"이라 `then`/`await`로 넘어옵니다.
그래서 `if (!response.ok)`로 직접 확인하고 `throw new Error(...)`를 던져
아래 `catch`에서 함께 처리되도록 했습니다.

**Q35. 403 레이트 리밋은 어떻게 처리했나요?**
GitHub API는 인증 없이 호출하면 **IP당 시간당 60회** 제한이 있습니다. 초과하면 403이 옵니다.
`response.status === 403`일 때 "GitHub API 호출 한도(시간당 60회)를 넘었습니다. 잠시 후
다시 시도해 주세요."라는 메시지를 던져 사용자가 원인을 알 수 있게 했습니다.
개발 중 새로고침을 반복하면 실제로 걸리기 때문에 반드시 필요한 처리였습니다.

**Q36. `try/catch`에서 `err instanceof TypeError`는 왜 확인하나요?**
인터넷이 끊겨 요청 자체가 실패하면 `fetch`는 `TypeError: Failed to fetch`를 던집니다.
이건 기술적인 메시지라 사용자에게 그대로 보여주면 의미가 없습니다.
그래서 `TypeError`면 "네트워크 연결을 확인해 주세요"로 바꾸고,
그 외(제가 직접 던진 상태 코드 에러)는 준비한 메시지를 그대로 보여줍니다.

**Q37. API로 받은 데이터를 그대로 화면에 넣어도 되나요?**
안 됩니다. 저장소 이름이나 설명에 `<img onerror=...>` 같은 문자열이 들어 있으면
`innerHTML`에서 태그로 해석되어 실행될 수 있습니다(XSS).
그래서 `escapeHtml()`로 `& < > " '`를 엔티티로 바꾼 뒤 넣습니다.

## F. 상태 관리 / 설계 ★ 이 과제의 핵심

**⭐ Q38. "이벤트 → 상태 → 렌더링" 흐름을 예를 들어 설명해 주세요.**
다크 모드로 설명하면,
1) **이벤트**: 토글 버튼 클릭 → `addEventListener('click', ...)` 콜백 실행
2) **상태 변경**: `state.theme`을 `'dark'`로 바꾸고 `localStorage`에 저장
3) **렌더링**: `renderTheme()`이 `<html data-theme="dark">`로 속성을 바꿈 → CSS 변수가 교체되며 전체 색 변경
중요한 건 클릭 핸들러가 색을 직접 칠하지 않는다는 점입니다.
핸들러는 상태만 바꾸고, 화면은 상태를 보는 렌더 함수가 담당합니다.

**Q39. 그렇게 나누면 뭐가 좋은가요?**
"지금 화면이 왜 이렇게 보이지?"의 답이 항상 `state` 한 곳에 있습니다.
같은 상태 변경이 여러 곳에서 일어나도(최초 로드, 재시도 버튼, 필터 클릭) 화면 그리는 코드는
하나라서 중복이 없고, 두 화면이 겹쳐 보이는 버그가 생기지 않습니다.

**⭐ Q40. 이게 React랑 무슨 상관인가요?**
React의 `useState`는 여기의 `state` 객체이고, `setState`는 여기의 `setProjectsState()`입니다.
차이는 React가 상태가 바뀌면 **렌더 함수를 자동으로 다시 호출**해 준다는 것뿐입니다.
지금은 제가 `renderProjects()`를 직접 부르고 있고, React는 그 호출을 대신해 줍니다.
컴포넌트도 여기서 `createProjectCard()`처럼 "데이터를 받아 UI를 반환하는 함수"와 같은 개념입니다.

**Q41. 지금 구조의 한계나 개선점은?**
1) 상태가 바뀔 때마다 목록 전체를 다시 그립니다. 항목이 수천 개면 비효율적이고,
   React처럼 바뀐 부분만 갱신하는 방식이 필요합니다.
2) `innerHTML`로 그리기 때문에 카드 안에 이벤트를 걸려면 위임이 필요합니다.
3) 파일이 커지면 `main.js` 하나로는 관리가 어려워지고, ES 모듈(`import/export`)로 나눠야 합니다.
4) 다크 모드가 첫 렌더에서 아주 잠깐 깜빡일 수 있습니다(아래 Q42).

**Q42. 새로고침할 때 다크 모드가 살짝 깜빡이지 않나요?** (날카로운 질문)
맞습니다. `defer` 스크립트는 HTML 파싱이 끝난 뒤 실행되기 때문에, 그 직전에 라이트 화면이
한 프레임 보일 수 있습니다. 해결책은 `<head>`에 아주 작은 인라인 스크립트를 두어
`data-theme`을 먼저 지정하는 것입니다.
이번에는 과제 요구사항인 "JS 파일은 defer로 연결"을 지키기 위해 인라인 스크립트를 쓰지 않았고,
대신 이 트레이드오프를 인지하고 선택했습니다.

## G. 접근성 / 기타

**Q43. 접근성을 위해 무엇을 했나요?**
시맨틱 태그, 의미 있는 `alt`, `label[for]` 연결에 더해
- 햄버거 버튼에 `aria-expanded`, 테마 버튼에 `aria-pressed`로 상태를 알림
- 상태가 바뀌는 영역(프로젝트 상태, 에러 메시지)에 `aria-live`/`role="alert"`
- `:focus-visible` 스타일을 지우지 않고 오히려 뚜렷하게 유지
- 맨 앞에 "본문 바로가기" 링크(Tab 을 누르면 나타남)
- `prefers-reduced-motion` 존중

**Q44. JS가 꺼져 있으면 어떻게 되나요?**
등장 애니메이션의 초기 상태(`opacity: 0`)는 `.js .reveal` 처럼 `<html class="js">`가 있을 때만
적용되도록 했습니다. `main.js`가 실행되면서 이 클래스를 붙이므로, JS가 죽으면 콘텐츠는
그냥 처음부터 보입니다. 애니메이션 때문에 본문이 영영 안 보이는 사고를 막기 위한 안전장치입니다.

**Q45. 이 프로젝트에서 가장 어려웠던 부분은?** (거의 반드시 나옵니다 — 본인 경험으로 바꿔 답하세요)
예시 답변: "비동기 상태 관리였습니다. 처음에는 로딩 표시와 카드 렌더링을 서로 다른 곳에서
지우고 그리다 보니, 에러가 났는데 이전 카드가 남아 있는 화면이 나왔습니다.
그래서 `renderProjects()` 한 함수가 상태에 따라 **항상 전부 다시 그리도록** 바꾸고,
상태 변경은 `setProjectsState()` 한 창구로만 하게 정리했더니 문제가 사라졌습니다."

**Q46. 다음에 개선한다면?**
저장소 목록 캐싱(같은 데이터를 반복 요청하지 않기), 페이지네이션, 폼 실제 전송(Formspree),
그리고 `main.js`를 기능별 모듈로 분리하는 것입니다.
